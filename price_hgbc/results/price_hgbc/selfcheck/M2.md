## 1. Pre-declared rules (written into `src/price_hgbc/m2.py` before any M2 number was computed)

* **2013 validation:** the group's own scheme, reused (`ablation/study.py` `temporal_folds`, `run.json`
  `tuning_validation_folds`). Fold 1 trains 2010-01-29 … 2012-12-31 and validates 2013-01-01 … 06-30. Fold 2 trains
  2010-01-29 … 2013-06-30 and validates 2013-07-01 … 12-31. The held-out probabilities are pooled (17,520 rows), and τ
  is searched on the pooled set with M1's `tune_tau` (0.30–0.70, 41 points, ties → closest to 0.5, then smaller).
* **Training start 2010-01-29**, aligned with P1's 28-day warm-up (rule D).
  M1 itself started at 2010-01-08, so M1_ref is re-fitted here under the M2 protocol (rule B).
* **2a:** M1 parameters on M1 features vs M1 + extended features. The extended set wins iff it gains ≥ 0.5 pp and the
  paired whole-day bootstrap 95 % CI (n_boot 1000, seed 0) excludes 0.
* **2b:** 48 configurations on the 2a winner, plus the reference row `M1_ref` (M1 parameters and features verbatim,
  same folds and τ search). Fixed: `early_stopping=False`, `random_state=17` (M1_ref keeps M1's 0; the seed is
  provably unused, see Task 2), `class_weight=None`, read from M1's `m1_run.json` and written to `m2_best_config.json`.
* **Ranking:** 2013 pooled BalAcc. Configs within < 0.05 pp of the top are tied; among them pick smaller
  `max_leaf_nodes`, then smaller `max_iter`, then larger `l2_regularization` (residual ties: higher BalAcc, then
  config_id).
* **Adoption:** best ≥ M1_ref + 0.5 pp on 2013 **and** paired CI excludes 0; otherwise "retain M1".
  2014 is evaluated once, after the decision, for confirmation only.

## 2. Self-check tables

### Task 1: P1 features and `extra_features.py`

**1.1 Where P1's features are.** There is no artefact labelled "feature table v1". The closest is the group ablation
`comp9417_project_kit/ablation/features.py` (commit `116e296`), function `build_features(data, day_type_train_end)`:
* Input: `load_study(path)`, which reads only up to 2015-01-01 00:00.
* Output: one wide frame (CORE, WEATHER, REGION, EXTRA_WEATHER, PRICE_SPIKES = `prev_price_max`,
  `prev_negative_slots`, DAY_TYPE, ROLLING), with day boundaries from `dayahead.market_day`.
* Day-by-day use: there is no per-day API (only as-of replays inside `validate_study`), and it fits a KMeans day-type model.
* Categorical encoding: one-hot weekday plus sin/cos period, so no native categorical columns.

Because it cannot serve 2015+ or per-day prediction, I wrote a compatible implementation instead
(`src/price_hgbc/extra_features.py`). It reuses P1's definitions, and the test shows they are bit-identical.

**1.2 Coverage of the required features**

**Spike-ratio rule:** `max(D) / max(P̄(D), 1 $/MWh)`. The denominator is floored at 1 $/MWh, so a zero or negative
daily mean gives a finite, sign-stable value. On the released data no day has P̄(D) < 1, so the floor never triggers
(count recorded by a test). A synthetic test exercises the zero and negative-mean cases.
